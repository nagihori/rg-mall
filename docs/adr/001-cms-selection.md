# ADR 001: コード管理できるヘッドレス CMS を採用する

## 状態

提案

## 背景

更新担当者は技術的な操作をせず、複数人で告知と写真をブラウザから更新する。一方で、デザインやコンテンツ構造は開発者が Git とコードで保守したい。

## 決定

初期案として、Next.js と Payload CMS を同一 TypeScript プロジェクトで運用する。コンテンツは PostgreSQL、写真は S3 互換ストレージへ保存する。

## 根拠

- 管理画面、ログイン、役割、下書き、メディアを一つの運用導線に集約できる。
- フィールド、検証、アクセス制御、公開画面をコードレビューと Git の変更履歴で管理できる。
- 公開サイトと管理画面が同じドメインモデルを共有でき、二重入力を避けられる。

## 代替案

- **Markdown + Git ベース CMS**: 開発者には扱いやすいが、更新担当者が Git の認証や変更の概念に触れやすく、今回の最優先体験に合わない。
- **SaaS 型ヘッドレス CMS**: 導入は速いが、料金、データ所在、スキーマ変更の自由度を契約に依存する。既存契約がある場合は比較対象にする。
- **従来型 CMS のテーマ運用**: 編集画面は馴染みやすいが、公開画面と管理画面の保守境界を明確に設計する必要がある。

## 影響

- サーバー運用、DB、ストレージ、バックアップが必要になる。
- 実装開始時に Payload の現行サポート状況、ホスティングとの互換性、既存 ID 基盤との連携可否を確認する。
- 運用開始前に、実際の更新担当者で 5 件程度の告知作成テストを行い、管理画面の補助文言を調整する。
