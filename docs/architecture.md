# Architecture

## 構成

```text
ブラウザ（更新担当者）
  └─ CMS 管理画面
       └─ 認証・権限確認
            └─ 正規化・検証・状態遷移
                 ├─ Supabase PostgreSQL（イベント、ユーザー、監査ログ）
                 └─ Vercel Blob（写真）

ブラウザ（プレイヤー）
  └─ Next.js 公開サイト
       └─ 公開済みイベント取得 → 表示用モデルへ変換 → キャッシュ再検証
```

## 責務分離

```text
src/
  app/          ページ、レイアウト、薄い route handler
  components/   公開画面の表示部品
  cms/          Payload collections、access control、管理画面設定
  lib/
    domain/     イベント状態・公開可否・一覧分類のルール
    normalize/  CMS 入力を内部モデルへ揃える処理
    validate/   Zod 等によるスキーマと業務検証
    presenters/ DB / CMS データを公開用モデルに変換
  styles/       デザイントークン、グローバル基盤、コンポーネント用 SCSS
```

- `app/` と `components/` は、確定した view model を表示する。
- `cms/` は編集体験、権限、保存時 hook を担当する。
- `lib/domain/` が日時にもとづく表示分類と状態遷移を所有する。
- `lib/normalize/` と `lib/validate/` が全入力の単一入口になる。
- DB とストレージの詳細を UI に漏らさない。

## データフロー

1. editor が CMS でイベントを保存する。
2. 保存 hook が空白、日時、slug、リッチテキスト、メディア参照を正規化する。
3. スキーマ検証と業務検証を通過したデータだけを DB に保存する。
4. reviewer が確認依頼を確認し、公開すると `publishedAt` と監査ログを確定する。
5. 公開イベントの変更を検知して、対象ページと一覧のキャッシュを再検証する。
6. 公開サイトは published のデータだけを取得し、presenter がカテゴリ・表示日時・画像 URL を作る。

確認依頼時には、サーバー側から Discord Incoming Webhook へ通知する。通知には CMS の確認画面への URL を含めるが、Discord のボタンやメッセージだけで公開状態を変更しない。Discord OAuth はログイン時に本人の Discord ID を取得するためだけに使い、role 判定は Supabase PostgreSQL のユーザーレコードで行う。

## 保存と公開

- **真実のデータ源**: Supabase PostgreSQL のイベント・ユーザー・監査ログ、および Vercel Blob 上の原本メディア。
- **更新単位**: イベント 1 件。本文・日時・写真は下書き版としてまとめて変更する。
- **競合**: 楽観ロックまたは最終更新日時の照合を行い、他者が更新済みなら上書き前に再読み込みを促す。
- **公開整合性**: 公開版と編集中の下書きを分離し、保存途中の変更を公開画面へ流さない。
- **キャッシュ**: 公開時・公開取消時にイベント詳細、一覧、アーカイブを再検証する。失敗時は再試行キューと管理者通知を用意する。

## 認証・権限

認証方式は組織の既存 ID 基盤を優先し、なければメールとパスワードを使う。role は DB 側で判定し、UI のボタン非表示だけでアクセス制御を済ませない。管理者操作は再認証または強いセッション要件を検討する。

初期実装では Discord OAuth を認証方式とし、最小権限の `identify` スコープのみを要求する。Discord のアプリ秘密鍵、OAuth client secret、Webhook URL は Vercel の環境変数に保存し、公開リポジトリやクライアントへ出さない。

Payload は `@payloadcms/db-postgres` で Supabase PostgreSQL に接続する。Vercel の実行環境では Supabase Shared Pooler の transaction mode 接続文字列を `DATABASE_URL` に使い、migration・`pg_dump`・復元には direct connection を使う。アプリの接続文字列と管理用接続文字列は分離し、後者を Vercel へ設定しない。

## 無料運用の境界

- Vercel Hobby と接続する各サービスの無料枠内だけで運用する。超過分を購入する設定は有効にしない。
- Vercel Hobby の利用は個人・非商用に限られるため、この前提を満たす運用だけを対象にする。商用化時は無料継続を前提にせず、ホスティングを見直す。
- Vercel Blob は公開メディア用の public store とし、原本・権利情報は DB とバックアップで管理する。画像サイズ上限、派生画像数、キャッシュを設計して転送量を抑える。
- 無料枠の到達が近い場合は管理者通知を行い、画像アップロードを停止して既存公開ページを優先する。
- Supabase Free は低アクティビティのプロジェクトを休止することがある。CMS と公開 API は、休止からの復帰直後に失敗した場合の再試行と、編集者向けの案内を用意する。無料枠を維持する目的だけの定期アクセスは実装しない。

## 障害と例外

- 入力不備: 該当フィールドに日本語で理由と修正方法を出し、下書きは失わせない。
- 画像処理失敗: イベントは保存できるが、公開・確認依頼は必要な画像処理が完了するまで止める。
- 再検証失敗: 公開状態は保存し、非同期で再試行する。管理者へ未反映を通知する。
- CMS 障害: 公開サイトは最後に成功したキャッシュを配信し、更新は一時停止する。
